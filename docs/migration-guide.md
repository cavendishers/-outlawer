# Migration Guide

## Policy

Every schema change must be delivered through Alembic.

This includes:

- new tables
- altered columns
- indexes
- constraints
- enum changes
- vector columns

## Required Tooling

- SQLAlchemy 2.x
- Alembic

## Rules

- do not manage schema in production with `create_all()`
- do not manually patch production tables
- do not merge model changes without the matching migration file
- review autogenerated migration files before committing
- prefer reversible migrations when practical

## Workflow

1. update SQLAlchemy models
2. generate a migration
3. review the migration script
4. apply it locally
5. run tests
6. commit models and migration together

## Example Commands

```bash
alembic revision --autogenerate -m "create_raw_assets_table"
alembic upgrade head
```

## Review Checklist

- correct table names
- correct column types
- correct foreign keys
- correct nullable settings
- correct unique constraints
- correct indexes
- safe downgrade path if applicable

## Deployment Rule

Database migration should run as an explicit release step before new API and worker containers start serving traffic.
